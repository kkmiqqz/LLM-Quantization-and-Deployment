 # Day 10: AWQ量化实战与 vLLM 云端极限推理

## 一、 核心理论前置：今天我们在解决什么问题？

在之前的 Day 6 - Day 9 中，我们使用 `llama.cpp` 和 GGUF 格式完成了**端侧（本地设备）**的部署，它的特点是单文件、轻量、适合单用户离线使用。
但在**云端（服务器）**，我们需要面临的是成千上万的用户同时发来请求。在这个场景下，`llama.cpp` 的并发能力不足，我们需要新的武器：**AWQ 量化算法** 与 **vLLM 推理框架**。

### 1.1 什么是 AWQ 量化？（保智商的艺术）
AWQ 全称是 **Activation-aware Weight Quantization（激活感知权重量化）**。
在 Day 5 我们学过，粗暴地把 FP16 压成 INT4，极个别的“离群点（Outliers）”会毁掉模型精度。之前我们了解过 GPTQ，它通过复杂的数学补偿来减少误差。而 AWQ 提出了一个极其聪明的洞察：

*   **洞察**：判断一个权重是否重要，不应该只看它自身的数值大小，而应该看**它对应的输入激活值（Activation）有多大**。如果某个通道的输入信号极强，那么连接这个通道的权重就绝不能乱砍。
*   **做法**：AWQ 通过少量的校准数据跑一遍，找出那仅占 **1%** 的“极其重要的权重通道”。然后，它在量化前对这些重要通道的权重进行**数学等价的放大（Scale up）**，同时把对应的输入除以相同的倍数。这样，权重的相对误差就变小了，而计算结果完全不变（不需要像 GPTQ 那样做复杂的反向传播）。

### 1.2 为什么云端要用 vLLM？
传统大模型（比如直接用 HuggingFace 跑）有两个致命伤：
1.  **KV Cache 显存浪费（碎片化）**：每个请求的上下文长短不一，系统必须按照最长上下文预留一大块连续显存，导致 60% 以上的显存被白白浪费。
2.  **GPU 经常在“发呆”**：传统批处理（Batching）要等一批请求全部生成完，才能处理下一批。如果有人生成了 1000 个字，有人只生成了 10 个字，那些早早结束的请求占用的 GPU 算力就被浪费了。

**vLLM 的核心魔法：**
*   **PagedAttention**：把操作系统的“虚拟内存分页”搬到了显存里。把 KV Cache 切成固定大小的块，物理上不用连续，显存利用率逼近 100%。
*   **Continuous Batching（连续批处理）**：只要 GPU 有一个槽位空出来，立刻塞入新进来的请求，让 GPU 永远处于满载运转状态。

使用 AutoAWQ 库，加载 FP16 模型，执行 128 组的校准数据，生成 4-bit 权重、16-bit 激活的模型。

## 三、 实验结果与硬核分析

### 1. 吞吐量数据对比
| 测试场景 | 总生成 Token 数 | 耗时 | 吞吐量 (tokens/s) |
| :--- | :--- | :--- | :--- |
| **单条请求 (Batch=1)** | 64 | 0.30s | **212.42** |
| **高并发请求 (Batch=16)** | 1024 (16 * 64) | 0.35s | **2902.20** |

### 2. 深度原理剖析（面试必考点）
**现象**：为什么并发（16条请求）时的总吞吐量，是单条请求的 **13 倍以上**，而总耗时几乎没有增加？

**原理解析**：
1.  **单条请求的瓶颈（Memory Bound）**：生成单个 Token 时，GPU 的 Tensor Core（算力）大量闲置，瓶颈纯粹在于显存带宽。每次都要把 1.1GB 的模型权重从显存搬运到寄存器，时间都花在“搬数据”上了。
2.  **Continuous Batching 的威力**：vLLM 将 16 个请求动态打包在一起同时计算（相当于一次矩阵乘法处理 16 个 Token）。此时，**显存带宽的“搬运成本”被 16 个请求共同平摊**，GPU 的算力被彻底填满。
3.  **Marlin 内核加速**：日志显示 vLLM 自动切换到了 `awq_marlin` 内核。Marlin 是针对 3090/4090 等 Ampere 架构极度优化的混合精度矩阵乘法内核，专门为 W4A16 设计，让计算速度进一步逼近极限。

## 四、 全景总结：端侧 vs 云端选型对比

| 维度 | llama.cpp (GGUF Q4_K_M) | vLLM (AWQ + Marlin) |
| :--- | :--- | :--- |
| **适用场景** | 端侧 / 离线 / 单用户 | 云端 / 在线服务 / 高并发 |
| **量化格式** | GGUF (单文件) | AWQ (HuggingFace 目录) |
| **显存占用** | ~0.9 GB | ~1.1 GB |
| **单条生成速度** | 185 t/s | 212 t/s |
| **并发能力** | 较弱 | **极强 (2902 t/s)** |

## 五、 踩坑实录（工程避坑指南）
1. **pip 撑爆系统盘**：直接 `pip install vllm` 会拉取最新的 CUDA 13 依赖，导致系统盘爆满。解决：安装指定兼容版本 `vllm==0.5.4 --no-cache-dir`，并清理缓存。
2. **幽灵依赖报错**：`outlines` 库依赖了远古 `pyairports` 包且文件缺失。解决：直接修改源码注释掉该 import。
3. **模型输出乱码（!!!!!!）**：vLLM 底层调用未加 `trust_remote_code=True` 导致 Qwen 聊天模板解析错误（不影响底层压测性能）。
