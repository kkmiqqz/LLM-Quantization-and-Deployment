## 💡 核心科普：什么是“模型量化”？

如果你是第一次接触大模型部署，看到“量化”、“端侧”、“W4A16”这些词可能会一头雾水。先用一个简单的比喻来理解。

**1. 通俗理解量化：从“无损音乐”到“MP3”**
大模型就像一首极其庞大的无损交响乐（比如 Qwen 1.5B 模型，用全精度保存需要 3GB 显存）。但很多播放设备（比如手机、车机、甚至普通的显卡）内存有限，装不下它。
**量化（Quantization）**，就像是我们把无损音乐压缩成 MP3。虽然损失了一点点微小的音质（精度），但文件体积缩小了 4 倍，在普通设备上也能流畅播放了。

**2. 量化究竟在做什么？**
在计算机底层，模型参数原本是用 16 位浮点数（FP16，占 2 个字节）或者 32 位浮点数（FP32，占 4 个字节）存储的。它们可以表示非常精确的小数。
量化的核心操作，就是把这几十亿个精确的小数，硬塞进 8 位（INT8）甚至 4 位（INT4）的整数格子里。
因为整数占用的字节更少，模型就“瘦身”了，不仅省显存，而且 GPU 计算整数乘法的速度，远远快于计算浮点数。

**3. 我们要量化哪些内容？**
在端侧部署的实际工程中，我们通常会进行混合量化（比如常见的 `W4A16`，代表权重用4位，激活用16位）。主要针对以下三个“吃显存”的大户：
*   **权重（Weights）**：模型那十几亿个固定参数，这是显存占用的绝对大头，通常被极致压缩到 INT4。
*   **激活值（Activations）**：推理时动态产生的大量中间计算结果，对精度极度敏感，通常保留 FP16 或轻量压缩。
*   **KV Cache**：大模型在生成文字时为了不重复计算而建立的“备忘录”，当上下文极长时，它会疯狂吃掉显存。

**4. 为什么量化这么难？**
因为模型不是简单的数字堆砌，里面的极个别的“异常值（离群点）”会毁掉一切。简单粗暴地压缩，会导致模型直接变傻。因此，我们需要研究 `AWQ`、`GPTQ` 等高级算法，在极限压缩体积的同时，保住模型的智商。

## 🔥 核心实验成果展示

在本项目的实操环节，我将 1.5B 的 Qwen2.5 模型在 RTX 3090 上进行了深度压测，得出了极具工程指导意义的结论：

- **端侧极限压缩**：通过 Q4_K_M 混合量化，模型体积从 **2.9GB 暴降至 0.9GB**。在长文本 Prefill 阶段，低比特模型凭借更小的显存带宽压力，吞吐量全面反超原生 FP16。
- **云端高并发极限**：使用 vLLM 部署 AWQ 模型，并开启 Marlin 汇编内核与 CUDA Graph，在 Batch=4 时达到 **714 tokens/s**，反超 FP16 原版 30%；并发首字延迟（TTFT）控制在 **2.93 ms**。
- **跨平台轻量化**：导出 ONNX 格式并使用 ORT GenAI 推理，速度达到 **116 t/s**，是原生 PyTorch 推理（15 t/s）的 **7.5 倍**。
- **无损编码探索**：结合数据压缩背景，对 Q8_0 权重进行定长索引与静态 Huffman 编码，在包含分块索引开销的情况下，仍实现约 **3.36%** 的额外存储收益。

## 🎯 项目全景总结：从端到云的全栈部署心智

经过这 15 天的硬核实战，我们不仅跑通了代码，更建立了一套大模型部署的工程心智：

| 方案 | 代表框架 | 适用场景 | 硬件依赖 | 核心优势 | 性能数据 (1.5B模型) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **端侧 GGUF** | llama.cpp | 手机/车机/离线设备 | 纯 CPU / 边缘 GPU | 极低内存映射（mmap），单文件分发 | 生成速度 **185 t/s** (Q4) |
| **云端 AWQ** | vLLM | Web API / 企业服务 | 数据中心 GPU | 显存池化，Continuous Batching | 并发吞吐 **714+ t/s** (Batch=4) |
| **跨平台 ONNX** | ORT GenAI | Windows/Mac/多端适配 | CPU / 各类 GPU | 静态图算子融合，无 Python 依赖 | 生成速度 **116 t/s** |
| **无损压缩 (探索)** | 静态 Huffman | 权重存储/网络传输 | 需配套高效解码器 | 基于真实频率分布，消除统计冗余 | 压缩率 **3.36%** |

**核心工程启示**：
1. **没有银弹**：量化算法的理论加速（如 AWQ），必须依赖底层推理引擎的 Kernel 优化（如 Marlin 汇编内核）才能真正转化为业务收益。
2. **场景决定架构**：边缘设备追求极致的 C++ 与低比特兼容（GGUF）；云端追求吞吐量与显存并发利用率（vLLM）；多端分发则看重轻量与通用（ONNX）。
3. **压缩的边界**：INT8 权重的零阶熵已经非常接近实际存储极限，继续榨取无损空间（如借助跨领域 Huffman 编码）需要极度警惕解码开销对 GPU 并行度的破坏。
