# Day 9: 量化模型输出质量评估与下游任务测试

## 一、 实验目的
端侧部署不能只看速度和体积，如果量化把模型变成了“傻子”，那毫无工程价值。今天的任务是通过两个核心指标来评估模型质量：
1. **困惑度 (PPL)**：衡量模型对长难文本预测的准确率，数值越低，模型越聪明。
2. **下游任务 (JSON 抽取)**：测试模型在严格指令遵循场景下，是否还能输出合法结构的数据。

## 二、 实验步骤与执行指令

### 1. 困惑度 (PPL) 测试
准备一段包含复杂学术论述的长文本 `data/ppl_text.txt`（约 1000 token），使用默认上下文窗口进行交叉熵计算。

```bash
# 测试三档模型的 PPL
./llama.cpp/build/bin/llama-perplexity -m models/qwen-f16.gguf -f data/ppl_text.txt -ngl 99
./llama.cpp/build/bin/llama-perplexity -m models/qwen-q8.gguf -f data/ppl_text.txt -ngl 99
./llama.cpp/build/bin/llama-perplexity -m models/qwen-q4.gguf -f data/ppl_text.txt -ngl 99
```

### 2. 下游任务 (JSON 抽取) 测试
使用 Python 脚本自动化调用 `llama-cli`，测试模型对设备日志的结构化提取能力。
```bash
python3 scripts/day09_quality_test.py
```

## 三、 实验结果与深度分析

### 1. 困惑度 (PPL) 数据对比
| 模型版本 | PPL 值 | 相对 FP16 的增幅 |
| :--- | :--- | :--- |
| **FP16 (原版)** | 13.4811 | 基准 |
| **Q8_0** | 13.4780 | -0.02% (在误差范围内，等同于无损) |
| **Q4_K_M** | 14.6524 | +8.7% (合理的有损压缩) |

**分析**：
- Q8_0 完美保留了原版的预测能力，PPL 几乎持平。
- Q4_K_M 的 PPL 上升了约 8.7%。但在大模型量化领域，10% 以内的困惑度损失换来 3 倍的体积缩小，是完全可以接受的。

### 2. 下游任务 (JSON 抽取) 结果
| 模型版本 | 实际输出结果 | 结构合法性 |
| :--- | :--- | :--- |
| **FP16** | `{"设备ID": "8848", "告警级别": "CRITICAL", "故障原因": "温度过高引发自动关机"}` | ✅ 合法且精准 |
| **Q8_0** | `{"设备ID": "8848", "告警级别": "CRITICAL", "故障原因": "温度过高引发自动关机"}` | ✅ 合法且精准 |
| **Q4_K_M** | `{"设备ID": "8848", "告警级别": "CRITICAL", "故障原因": "温度过高引发自动关机"}` | ✅ 合法且精准 |

**分析**：
三档模型均完美遵循了指令，没有任何废话，输出了合法的 JSON 并且成功提取了所有字段。这证明了即使量化带来了微小的 PPL 退化，但在具体的结构化任务（如设备控制、信息抽取）中，模型的逻辑底座依然稳固。

### 3. 意外之喜：短文本下的量化速度碾压
在跑 JSON 测试时，我们也观测到了速度数据：
- FP16：Prompt `1273.6 t/s` | Generation `150.1 t/s`
- Q8_0：Prompt `4523.9 t/s` | Generation `190.1 t/s`
- Q4_K_M：Prompt `4188.3 t/s` | Generation `214.9 t/s`
在短 Prompt 场景下，量化版本的预填充速度达到了原版的 **3 倍以上**，生成速度也提升了约 30%-40%。

## 四、 工程决策
**提问**：“你在部署端侧模型时，如何评估量化模型的质量？”
> **你的回答**：“在端侧部署中，速度、体积和精度是一个不可能三角。以我实测的 Qwen 1.5B 为例，在长难句的严苛测试下，Q8_0 的 PPL 几乎与原版完全一致，适合对精度要求极高的场景；而 Q4_K_M 的 PPL 虽然上升了约 8.7%，但在 JSON 抽取等下游任务中依然表现完美。因此，如果设备显存极度受限，Q4 是完美的首选；如果对复杂逻辑推理要求极高，则应该选择 Q8。并且我实测发现，即使是短文本，量化模型也能带来 3 倍以上的预填充加速。”
