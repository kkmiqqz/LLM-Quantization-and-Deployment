# Day 15 Qwen INT8 量化后无损编码探索

**目标**　结合轨迹压缩经验，检验量化整数能否进一步无损压缩，并分析编码收益、元数据与 GPU 解码之间的取舍。

## 一、思路来源与方法选择

在之前的轨迹压缩工作中，我接触过“浮点数量化后，再对整数进行编码”的流程。因此想到：模型量化后的权重同样是整数，是否也能通过无损编码缩小存储，同时保留原量化模型的数值结果？

> 浮点权重 → 量化整数及尺度 → 无损编码 → 解码恢复量化表示 → 推理。

这里的“无损”针对已有量化表示，不意味着恢复原始 FP16 权重。可迁移的是分布分析、编码设计和解码成本评估；轨迹的相邻连续性不能直接假设存在于权重数组中。

本次先研究已有的 INT8 模型，比较两条路线：

- **定长索引＋例外流**：主体定位规则，尝试降低并行解码的复杂度。
- **静态 Huffman**：按真实符号频率分配码长，检验定长方案是否遗漏统计冗余。

### 1.1 其他方法为什么没有继续实测

除了实验的这两种办法，其实一开始还有其他几种备选，但是在理论分析或初步实验之后发现实验价值不大，所以没有再进一步实验。
| 方法 | 本次暂未选择的原因 |
| --- | --- |
| Gamma／Rice | 码长主要依据整数幅度及编码参数，未必匹配真实频率；先用按频率构造码字的 Huffman 建立基线，避免直接套用轨迹小残差的经验。 |
| rANS | 初期优先选择便于检查码长的 Huffman；实测后其平均码长距零阶熵仅约 0.0235 bit，说明同一概率模型下进一步收益有限，暂不追加实现。 |
| RLE／零游程 | 尚未统计到长重复游程的证据，零值较多也不能直接证明游程编码有效；本轮先验证符号频率冗余。 |
| Bitpacking／FOR | Q8_0 整数已经紧凑存为每个 1 字节，普通重新打包不会省空间；FOR 需要另测块内范围与基值开销，本轮先以固定索引方案检验规则解码表示。 |

ZipServ 的固定分类码与例外回退提供了结构参考，但其 BF16 指数压缩收益不能直接迁移到 INT8，本次未复现该系统。[3]

### 1.2 定长与变长编码在模型压缩中的适用性

| 表示方式 | 适用条件与场景 | 解码成本特点 |
| --- | --- | --- |
| 固定宽度／块内定长 | 数据范围或符号集合可缩小，且需要频繁、并行访问权重 | 块起点已知后，第 $i$ 个码字偏移可由 $ib$ 计算；处理步骤与单次读写量较规则 |
| Huffman／rANS 等变长表示 | 概率分布偏斜，节省的存储或传输成本足以补偿解码；可用于文件加载、权重传输，也可经专门设计用于在线推理 | 需要处理码字边界或状态依赖，通常通过独立码流、索引和查表增加并行性 |
| 定长主体＋例外流 | 常见集合覆盖率高，少量例外可单独保存 | 主体容易定位，但例外的识别、定位与额外访问仍有成本；整体长度并不固定 |

**定长更好控制，主要指地址计算和工作量更可预测**，便于线程分工、向量化访问和计算融合；不代表它一定更省空间或一定更快。模型量化本身常用固定低位宽表示，而量化后的额外无损压缩仍需找到可去除的冗余，不能直接截掉有效位。

变长编码也能在 GPU 上运行，同一条指令可以处理不同偏移，并非码长不同就必然与 SIMT 冲突。困难在于边界／状态依赖、工作不均和访存组织。因此，本次同时考察规则表示与 Huffman，并把分块索引开销纳入长度测试；实际解码延迟仍需另测。

## 二、实验对象与成本口径

模型为 **Qwen2.5-1.5B 的 `qwen-q8.gguf`**，路径为 `/root/rivermind-data/models/qwen-q8.gguf`。脚本放在 `/root/qwen-codec`，在现有 Python 3.10 环境中使用 NumPy 和 gguf，计算在 CPU 上完成。

`inspect` 实际读到 **197 个 Q8_0 张量、141 个 F32 张量**。当前只统计 Q8_0 整数；F32 参数不处理，量化尺度原样保留。

Q8_0 每块保存 **32 个 INT8 整数＋1 个 FP16 尺度**，共 34 字节，因此原始成本为 **8.5 bit/权重**。[1] 比较整数编码长度时基线是 8 bit；比较包含尺度的 Q8_0 数据时基线是 8.5 bit，两者不能混用。

### 2.1 定长索引＋例外流

每个张量统计频率，选出最多 `2^b−1` 个高频整数建立 LUT，测试 `b∈{4,5,6,7}`。每个位置保存固定 `b bit` 索引，`0` 表示例外，例外值按顺序另存完整 INT8。

设例外比例为 $p_b$，整数主数据的平均成本为：

$$
B_{\mathrm{fixed}}=b+8p_b.
$$

获益的必要条件为 $b+8p_b<8$，尚未计入 LUT 等额外开销。例如 `b=7` 时，例外率必须低于 **12.5%**。

原型采用张量级 LUT；本次执行的是频率统计与长度估算，没有提供真实权重编码回解结果。

### 2.2 静态 Huffman 与分块测试

每个张量根据实际频率构造一张 Huffman 码表，统计符号出现次数 $n_x$ 和码长 $l_x$，得到精确主码位数：

$$
B_{\mathrm{Huffman}}=\sum_x n_xl_x,\qquad
L=\frac{B_{\mathrm{Huffman}}}{\sum_x n_x}.
$$

无需生成完整比特流，就能确定使用该码表时的主码长度。Huffman 在给定分布下使逐符号二进制前缀码的平均长度最小。[2]

空间估算明确采用以下口径：

| 保存内容 | 计算方式 |
| --- | --- |
| 主码流 | 按实际码长累加，各条码流单独补齐至字节 |
| Q8_0 尺度 | 保留原始字节数 |
| 码表 | 每张量 256 字节，保存规范 Huffman 码长 |
| 记录头 | 假定每张量 32 字节 |
| 分块索引 | 分块实验中假定每条码流 16 字节 |

先测试每张量一条连续码流，再按 **4096 个整数**切分独立码流。分块仍共享该张量的码表，因此平均码长不变，增加的是索引及填充成本。16 字节是当前索引布局假设，并非 Huffman 的固定要求。

**精确的是主码长度；码表以外的容器布局仍属于估算。** 本次没有实际写出 Huffman 比特流、执行解码或测量 GPU 性能，也未包含完整新容器目录和额外对齐。

## 三、执行步骤

沿用已能正常读取 GGUF 的环境，没有为本次测试重新升级依赖。

```bash
cd /root/qwen-codec
MODEL="/root/rivermind-data/models/qwen-q8.gguf"

# 检查张量类型
python q8_codec_probe.py inspect "$MODEL"

# 首个 Transformer 块：定长索引＋例外流
python q8_codec_probe.py analyze "$MODEL" \
  --csv q8_report.csv

# 同一组张量：每张量一条 Huffman 码流
python q8_huffman_probe.py "$MODEL" \
  --csv q8_huffman_report.csv

# 同一组张量：每 4096 个整数切分码流
python q8_huffman_probe.py "$MODEL" \
  --stream-weights 4096 \
  --csv q8_huffman_4096.csv

# 全部 Q8_0 张量：统一采用 4096 分块口径
python q8_huffman_probe.py "$MODEL" \
  --all --stream-weights 4096 \
  --csv q8_huffman_all_4096.csv
```

上述 CSV 均已生成。脚本为只读分析，不修改模型；输出文件已存在时，重跑需更换 CSV 文件名。`MODEL=...` 是当前终端的变量设置，未设置时传入空路径会报 `FileNotFoundError`。

全量 Huffman 报告也根据相同频率计算了定长方案成本，因此可以检查定长方案在全部张量上的适用性。

## 四、实验结果与分析

### 4.1 定长方案：例外成本抵消了索引节省

首块 7 个张量的最佳候选均为 `b=7`，整数数据成本为 **8.602～8.797 bit/整数**，已经超过原始 8 bit。

以 `blk.0.attn_k.weight` 为例：

$$
7+8p\approx8.716
\Rightarrow p\approx21.45\%.
$$

例外率明显超过 12.5% 的获益门槛。每个位置先付出 7 bit，约五分之一的位置还要追加完整整数，导致膨胀。

全量报告进一步确认：**197 个张量的最佳定长候选成本全部超过 8 bit**，范围为 **8.118～8.810 bit/整数**。`best b` 只代表候选间最优，不代表优于原始表示。这套方案应回退原始 INT8 保存，暂不开发 GPU 解码内核。

### 4.2 Huffman：存在小幅且普遍的空间收益

以下原始字节数均指所选 Q8_0 张量，包含尺度；编码空间包含第二节约定的元数据。

| 实验范围 | 加权 Huffman 码长（bit/整数） | 原始字节数 | 编码空间估算 | 节省比例 |
| --- | ---: | ---: | ---: | ---: |
| 首块 7 张量，连续码流 | 7.6912 | 49,717,248 | 47,913,137 | **3.63%** |
| 首块 7 张量，4096 分块 | 7.6912 | 49,717,248 | 48,100,895 | **3.25%** |
| 全部 197 张量，4096 分块 | 7.6818 | 1,640,042,496 | 1,584,890,222 | **3.36%** |

全量实验涉及 **1,543,569,408 个整数**，全部 197 个张量都有正收益，估计共节省 **55,152,274 字节，约 52.60 MiB**。首块结果与整体接近，没有遗漏能大幅改变总体量级的张量。

这不是完整 GGUF 文件的实测压缩率：F32 张量、原有 GGUF 元数据未参与统计，新的完整容器也未生成。

### 4.3 分块付出了多少空间成本

首块按 4096 个整数切分后，共有 **11,424 条码流**。相比连续码流，增加：

- 索引 **182,784 字节**；
- 字节填充 **4,974 字节**；
- 合计 **187,758 字节**，使收益从 3.63% 降至 3.25%。

若每块有 $K$ 个整数、索引为 16 字节，则平均索引成本为 $128/K$ bit/整数。`K=4096` 时为 **0.03125 bit/整数**；`K=256` 时则为 **0.5 bit/整数**，仅索引就可能超过当前冗余空间。

因此，小块有利于提供独立解码任务，却需要更多索引；大块降低空间开销，块内仍存在连续解码工作。本次只验证这一空间取舍，没有验证最优并行粒度。

### 4.4 为什么收益有限，换编码器是否值得

全部张量的加权零阶熵为 **7.6583 bit/整数**，Huffman 为 **7.6818 bit/整数**，相差约 **0.0235 bit**。在相同的逐张量零阶模型下，Huffman 已接近熵，更换 ANS 等编码器能够继续争取的空间有限。

Q8_0 按局部块尺度归一化整数。[1] 因此，浮点权重集中在零附近，并不能直接推出量化码字也高度集中；本次实际分布才是判断依据。**INT8 位宽更大，不等于天然存在较大的额外压缩空间。** 零阶熵也不是所有编码方法的普遍下限，局部条件分布和相关性需要另行验证。

层间虽有差异，但没有改变整体结论：V 权重的加权收益约 **4.27%**，单张量最高约 **6.67%**；三个 FFN 权重类型体积最大，贡献了约 **75.5%** 的总节省量。评价整体收益必须按字节数加权，不能挑最高层或简单平均各层百分比。

## 五、实验结论与个人思考

这次从数据压缩背景出发，把熟悉的量化后编码思想迁移到了真实模型权重上，并通过成本公式与实测频率筛选方案：**固定索引＋例外流发生膨胀，Huffman 在当前分块与元数据口径下可节省约 3.36% 的 Q8_0 数据空间。**

需要区分三种验收：能够无损还原、能够减少存储、能够改善部署性能。本次完成的是分布与编码长度分析；没有实际压缩文件、回解速度、显存下降或推理加速的证据。在线解码还可能增加计算、同步和临时读写，抵消这几个百分点的空间收益。

因此，本阶段保留脚本和 CSV，暂缓 GPU 实现。它的价值在于形成了“背景迁移 → 提出假设 → 建立成本模型 → 全量验证 → 决定是否继续投入”的过程，而不是将长度估算包装成部署加速成果。
