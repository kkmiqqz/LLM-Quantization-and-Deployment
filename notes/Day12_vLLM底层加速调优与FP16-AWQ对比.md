# Day 12: vLLM 底层加速调优与 FP16/AWQ 严格对比

## 一、 实验理论和目的
在 Day 11 的初步测试中，我们发现 AWQ 的推理速度竟然比 FP16 略慢。为了探究这是否是框架配置问题，今天我们进行严格的“控制变量”实验。首先认识两种模式的区别：
### 1. CUDA Graph（计算图捕获）
在传统的 `Eager` 模式下，GPU 每生成一个 token，CPU 都要向 GPU 发送几十条启动指令（Kernel Launch）。如果 CPU 调度耗时大于计算本身，GPU 就会闲置。**CUDA Graph** 把整个计算流程预先“录”成一张静态图，下次直接整图下发，彻底消除 CPU 的调度开销。

### 2. awq_marlin 汇编级内核
`vLLM` 默认的 `awq` 内核使用常规 CUDA Core 进行反量化。而 `Marlin` 是专门针对 Ampere 架构（如 RTX 3090）手写的汇编级内核，它利用 Tensor Core 直接完成混合精度矩阵乘法，彻底抵消了反量化带来的计算税。

主要验证两点：
1. `Eager` 模式（逐算子执行）与 `CUDA Graph`（图捕获）对推理速度的影响。
2. 开启 `awq_marlin` 汇编级内核后，AWQ 能否实现性能反杀。

## 二、 实验参数配置
为了确保公平，我们使用了相同的测试脚本 `day12_vllm_compare_plus.py`：
- **输入 Prompt**：固定为“请写一段快速排序的 Python 代码。”
- **生成长度**：`max_tokens=32`
- **并发设置**：`Batch=4`
- **显存限制**：`gpu_memory_utilization=0.4`（防止预分配吃光显存，方便观察纯权重差异）
- **关闭前缀缓存**：`enable_prefix_caching=False`

**对照组配置差异：**
- **组别 A (FP16)**：不量化，`enforce_eager=False` (开启 CUDA Graph)。
- **组别 B (AWQ)**：`quantization="awq_marlin"`，`enforce_eager=False`。

## 三、 实验结果：两次测试的数据对比

### 实验一：Eager 模式 + 默认 AWQ 内核
在这个配置下，vLLM 关闭了 CUDA Graph，且使用了未完全优化的 `awq` 内核。
- FP16：速度 **289.80 t/s**，显存 18355 MiB
- AWQ：速度 **283.51 t/s**，显存 18405 MiB
- **结果**：AWQ 不仅没变快，反而略慢。显存由于预分配吃满了，看不出差距。

### 实验二：CUDA Graph + Marlin 内核
在这个配置下，开启了所有底层加速。
| 测试配置 | 权重体积 | 生成速度 (Batch=4) | 分配的 KV Cache 块数 | 显存总占用 |
| :--- | :--- | :--- | :--- | :--- |
| **FP16 (原生)** | 2.89 GB | 550.51 t/s | 11944 | 8937 MiB |
| **AWQ (Marlin)** | **1.10 GB** | **714.07 t/s** | **16488** | 8979 MiB |

## 四、 深度原理剖析

### 1. 为什么组别 A 到组别 B 发生了惊天逆转？（550 t/s vs 714 t/s）
- **Marlin 内核的魔法**：`awq_marlin` 是专门为 Ampere 架构（如 RTX 3090）编写的底层汇编内核。它利用 Tensor Core 直接执行混合精度矩阵乘法，极大地抵消了“反量化”带来的计算税，让 AWQ 速度直接反超 FP16 约 **30%**。
- **CUDA Graph 的降维打击**：关闭 `enforce_eager=True` 后，vLLM 会把整个计算流程“录”成一张图，大幅减少了 CPU 频繁向 GPU 下发指令的调度开销。两次实验的速度提升（289 -> 550）主要归功于此。

### 2. 为什么 AWQ 权重小了一半，但总显存没有减少？
- 这是 vLLM 的 **显存池化（Memory Pooling）** 机制。在设置了 `gpu_memory_utilization=0.4` 后，vLLM 会“吃满”允许的显存。
- AWQ 省下的 1.8G 权重显存，被直接转化为了 **KV Cache 块**。看日志：FP16 只有 11944 个块，而 AWQ 多出了 4544 个块（16488个），**并发容量直接提升了 38%**。
- 结论：云端量化的真正目的，不是为了省显存，而是为了在同样的显存下，塞下更多的并发用户。

## 五、 全景总结：端侧 vs 云端选型指南

结合整个项目的实测数据，我们得出了终极的工程选型结论：

| 维度 | 端侧 (llama.cpp + Q4_K_M) | 云端 (AWQ + vLLM + Marlin) |
| :--- | :--- | :--- |
| **权重体积** | **0.9 GB** (极致压缩) | 1.1 GB (W4A16) |
| **依赖环境** | 纯 C++，零依赖，可脱离 Python | 依赖 CUDA/PyTorch 环境 |
| **单条生成速度** | 185.7 t/s | **714.0 t/s** (极限调优) |
| **并发吞吐能力** | 极弱（无动态批处理） | **极强** (理论超 2900+ t/s) |
| **首字延迟 (TTFT)** | 较高 (取决于 CPU 算力) | **极低** (并发低至 2.93ms) |
| **PPL (困惑度)** | 14.65 (损失 8.7%，但满足单机对话) | 13.47 (几乎无损) |

**选型结论：**
- **离线/边缘设备（手机、车机、无网环境）**：首选 GGUF。单文件分发，C++ 引擎对 CPU 内存利用极其极致。
- **在线高并发服务（Web API、企业知识库）**：必须选 AWQ + vLLM。其 PagedAttention 和 Marlin 内核能将 GPU 吞吐量压榨到极限，摊薄单次请求成本。

## 六、 面试大杀器：全链路问题应对

**Q：你在调优 vLLM 时，怎么把 AWQ 的性能压榨到极致？**
> 答：“量化算法的理论加速，必须依赖底层框架的 Kernel 实现。我通过切换 `awq_marlin` 汇编级内核抵消了反量化开销，并关闭 `enforce_eager` 启用 CUDA Graph 消除 CPU 调度开销。最终在 Batch=4 时，AWQ 达到 714 t/s，反超 FP16 30%。同时，利用 vLLM 的显存池化，AWQ 省下的体积转化为 KV Cache 块，使并发容量提升了 38%。”

**Q：大模型的 Prefill 和 Decode 两个阶段，哪个是算力瓶颈，哪个是访存瓶颈？**
> 答：“Prefill 是计算密集型（Compute Bound），Decode 是访存密集型（Memory Bound）。在 Decode 阶段，每次只生成一个 token，算力大量闲置，时间全花在把权重从显存搬到计算核心上。所以量化权重对 Decode 速度的提升极其明显。”

**Q：你在项目中遇到的最大挑战是什么？**
> 答：“基础设施环境的适配。我在云服务器上遇到了由于系统盘爆满导致的 `libcuda.so.1` 驱动损坏、vLLM 最新版依赖撑爆系统盘、以及模型存储在数据盘软链接导致的路径迷失。这些排雷经验让我深刻理解了 Linux 底层和 CUDA 环境运作机制。”
